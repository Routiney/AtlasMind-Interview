# 第五节课学习笔记：全栈面试助手 MVP 总结

本节课把前几节学习的内容串成了一个可以运行的全栈 MVP。重点不是一次性做完所有业务模块，而是理解浏览器、Java 后端、数据库和 Python Core 之间如何协作，并建立一套可以继续扩展的基础结构。

## 1. 本节课的总体目标

完成一个带认证、聊天会话和简历档案的个人面试助手：

- 用户可以注册、登录并访问受保护页面。
- 前端通过统一请求层调用后端 API。
- 后端验证登录身份，并保证用户只能访问自己的数据。
- 面试助手可以管理多个 conversation。
- 消息按分页加载，聊天输入框固定在卡片底部。
- 简历档案保存到后端数据库，而不是只保存在浏览器。
- 简历档案和面试助手共用同一个外层工作区布局。

## 2. 项目中的服务分工

| 服务 | 主要职责 |
|---|---|
| `web` | React 页面、路由、表单、聊天交互、请求状态和错误提示 |
| `server-spring` | Java/Spring API、JWT 认证、权限检查、数据库访问 |
| `server` | Python Core 或 Agent 执行层，负责生成面试回答和流式事件 |
| PostgreSQL | 保存用户、会话、消息和简历档案 |

浏览器不应该直接访问数据库，也不应该直接决定用户是否有权限。浏览器只负责发起请求，真正的身份和权限判断必须在后端完成。

## 3. 认证与路由保护

### 3.1 登录流程

1. 用户在前端输入用户名和密码。
2. 前端调用登录 API。
3. 后端校验用户名和密码。
4. 后端签发 JWT access token。
5. 前端保存 token，并在后续请求中加入：

```http
Authorization: Bearer <access-token>
```

6. 后端每次收到受保护请求时重新验证 token。

### 3.2 为什么不能只保护前端

前端代码、按钮和路由都可以被用户绕过。用户可以直接使用浏览器开发者工具、curl 或 Postman 发请求。因此：

- 隐藏按钮不是权限控制。
- 前端跳转登录页不是权限控制。
- 后端必须验证 token。
- 后端必须根据 token 中的用户身份查询数据。
- 查询和修改数据时必须检查资源是否属于当前用户。

正确的权限模型是：

```text
请求 -> 解析 token -> 得到当前用户 -> 查询 user_id 对应的数据 -> 返回结果
```

而不是让前端传入一个 userId，然后后端无条件相信它。

### 3.3 路由保护

前端使用受保护路由区分公开页面和登录后页面：

- `/login`、`/register`：公开页面。
- `/workbench`、`/resume`：需要认证。
- 未登录访问受保护页面时，前端跳转到 `/login`。
- 这只是用户体验层的保护，后端 API 仍然必须独立验证 JWT。

开发自动登录还遇到过一个典型问题：初始状态被错误设置为“匿名”，导致直接访问 `/resume` 时先跳到登录页，自动登录后又跳回 `/workbench`。修复方式是：开发自动登录开始验证时，先使用 `checking` 状态，验证完成后再决定是否渲染页面。

## 4. 统一 API 请求层

前端没有在每个组件里重复写 `fetch`，而是集中到 `apiClient.ts`：

- 统一拼接 API 地址。
- 统一添加 Bearer token。
- 统一解析 JSON 响应。
- 统一处理非 2xx 状态。
- 统一处理 401 未授权事件。
- 支持普通 JSON 请求和 SSE 流式请求。

这样做的好处是：后端接口格式或认证策略变化时，只需要修改请求层，不需要逐个修改页面组件。

## 5. Conversation 和 Message 数据模型

### 5.1 会话和消息分开

一个 conversation 可以包含多条 message：

```text
User
  ├── Conversation A
  │     ├── Message 1
  │     ├── Message 2
  │     └── Message 3
  └── Conversation B
        ├── Message 4
        └── Message 5
```

会话保存标题和更新时间，消息保存角色、内容、创建时间以及所属会话。

### 5.2 后端权限检查

读取会话、修改标题、删除会话和读取消息时，都必须同时检查：

```text
conversation.id = 请求中的会话 ID
conversation.user_id = 当前登录用户 ID
```

否则用户只要猜到另一个会话的 ID，就可能读取或删除别人的数据。

## 6. 消息分页与聊天窗口逻辑

不能在页面打开时一次性加载所有消息。消息数量增长后，会造成：

- 数据库查询变慢。
- 网络响应变大。
- 浏览器渲染变慢。
- 页面占用更多内存。

当前实现采用分页：

- 会话列表默认加载一页。
- 消息默认加载最新一页。
- 后端按创建时间倒序查询最新消息。
- 前端收到后反转为聊天阅读顺序。
- 点击“加载更早消息”时，读取下一页并插入到消息顶部。

聊天窗口的布局要点是：

```text
聊天卡片
  ├── transcript：可滚动消息区域
  └── composer：固定在底部的输入区域
```

关键 CSS 思路：

- 外层卡片使用固定高度或视口高度约束。
- 消息区域使用 `flex: 1`、`min-height: 0` 和 `overflow: auto`。
- 输入框不放在消息滚动区域内部。
- 消息增加时，滚动的是 transcript，而不是整个页面。

这解决了“对话越多，输入框越往下”的问题。正常聊天体验应该是消息区域内部滚动，输入框始终可见。

## 7. 面试助手界面结构

当前页面分为两层导航：

```text
外层侧边栏
  ├── 面试助手
  ├── 简历档案
  ├── 岗位匹配
  ├── 知识库
  ├── 模拟面试
  └── 复盘记录

面试助手主体
  ├── 会话列表侧边栏
  └── 当前会话聊天卡片
```

点击“简历档案”时，仍然保留外层侧边栏，只替换右侧主体内容。这比跳到一个完全独立的页面更适合工作台产品，因为用户不会丢失当前位置和导航上下文。

## 8. 简历档案模块

简历档案包含以下字段：

- 姓名
- 目标岗位
- 个人简介
- 教育经历
- 实习经历
- 项目经历
- 专业技能

前端使用受控表单：

- 输入框的值来自 React state。
- `onChange` 更新 state。
- 提交时调用后端 `PUT /api/resume`。
- 页面加载时调用 `GET /api/resume`。

后端使用当前登录用户的 `user_id` 保存档案，并通过唯一约束保证一个用户对应一份简历档案。

这里体现了一个重要原则：简历内容属于用户数据，因此应该存储在后端，而不是只存储在 localStorage 中。

## 9. 前端表单和错误处理

前端验证适合提供即时反馈，例如：

- 用户名不能为空。
- 密码长度不足时立即提示。
- 简历字段超过最大长度时提示。

但前端验证不能替代后端验证。后端仍然必须重新检查：

- 必填字段。
- 字符串长度。
- 当前用户身份。
- 请求数据格式。

用户体验上还需要区分几种状态：

- 加载中。
- 保存中。
- 保存成功。
- 网络错误。
- 登录过期。
- 没有数据。

## 10. 本节课排错经验

### 10.1 前端页面突然无法打开

先看浏览器控制台和 Network，再检查：

1. Vite 是否正在运行。
2. API 请求是否返回 401 或 500。
3. React 是否在初始化时把数组误当成分页对象。
4. 受保护路由是否发生了错误重定向。

本项目中曾经出现过分页接口返回对象，但前端仍然把返回值当数组使用，导致工作台初始化失败。修复后前端使用 `result.items`。

### 10.2 简历页没有侧边栏

原因是简历页直接作为独立页面渲染，没有复用工作台外壳。解决方式是让 `/resume` 使用和 `/workbench` 相同的布局组件，只替换右侧主体内容。

### 10.3 聊天输入框不断下移

原因是消息列表和输入框处在同一个普通文档流中，消息增长会把输入框推到页面底部。解决方式是建立固定高度的聊天卡片，并让只有消息 transcript 滚动。

## 12. 本节课的核心结论

这节课最重要的不是记住某个 React 写法，而是建立下面这条完整思路：

```text
用户操作
  -> React state
  -> 统一 API 请求层
  -> Spring Controller
  -> 认证和权限检查
  -> Service / Repository
  -> PostgreSQL
  -> 返回数据
  -> React 更新页面
```

只要这条链路清楚，后面的岗位匹配、知识库、模拟面试和复盘记录都可以沿用同样的模式继续开发。
